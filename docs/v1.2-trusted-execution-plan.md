# v1.2 可信执行底座与外部业务查询目标实施计划

> 状态：已在 `feature/v1.2-trusted-execution` 完成主体实现；v1.1 五模块真实模型 smoke 仍是独立发布门槛  
> 基线提交：`d078a7d`  
> 适用版本：`v1.2.0`～`v1.2.3`  
> 权威上游：`docs/project-plan.md`、`docs/module-plan.md`、`docs/upgrade-roadmap.md`  
> 执行 Prompt：`docs/claude-code/v1.2-trust-and-data-upgrade-prompts.md`

## 1. 目标

v1.2 不增加第六个 Copilot，也不扩展为 IAM、数据源管理平台或工作流引擎。目标只有两类：

1. 把 Data、Support、Report、Resume 的高风险对象升级为可持久化、可授权、可并发保护、可审计的可信动作。
2. 把 Data Copilot 升级为可安全接入一个外部只读 PostgreSQL 或 MySQL 业务库的参考实现。

完成后必须满足：

- token 与对象、操作者、状态和有效期绑定，数据库只保存 token 摘要。
- 跨 actor、过期、重放、并发确认和确认/取消竞争只有合法路径成功。
- 五个业务模块不依赖宿主扫描 `dev.qcoding.businesscopilot` 根包。
- 审计能够准确回答谁创建、谁执行、使用了什么模型/Prompt/policy、耗时多少，以及何时清理。
- PostgreSQL/MySQL 使用同一组 Data 只读查询契约。

## 2. 升级前代码基线

| 领域 | 当前实现 | v1.2 缺口 |
|---|---|---|
| Data candidate | `ConcurrentHashMap`，保存明文 token 和问题文本 | 重启丢失、无 owner、无定时清理、无数据库条件消费 |
| Support draft | PostgreSQL 条件消费明文 token | 无 owner/状态列，token 明文，工单状态更新缺 expected-state |
| Report draft | PostgreSQL 状态条件更新，token 明文 | 无 owner，按 ID 导出无对象授权，token 查询未绑定 actor |
| Resume job/assessment | JDBC 条件更新，token 明文 | 无 owner/reviewer queue，criteria/review token 未绑定 actor |
| 请求身份 | `BusinessRequestContext` 只有 requestId、actorId | 业务模块无法读取稳定角色集合和对象访问决策 |
| 自动配置 | Data 显式注册 Controller；其余依赖主应用扫描 | Resume Mapper 也依赖宿主扫描/手工 Bean |
| AI 元数据 | 业务服务自行读取 modelName | 无 provider、token usage、Prompt hash、finish reason、request id |
| Data 外部库 | 可选第二 DataSource，PostgreSQL metadata 实现 | 无权限诊断、column allowlist、方言接口和 MySQL |

## 3. 已确定的架构决策

### 3.1 创建窄 `platform/common-security`

创建条件已经满足：Data、Support、Report、Resume 四个模块都需要相同的 actor/role 读取和对象授权语义。

该模块只提供：

- `CurrentActor(actorId, roles)`。
- `CurrentActorProvider`。
- `BusinessRole`：`ADMIN`、`OPERATOR`、`REVIEWER`。
- `ObjectAction` 和 `ObjectAccessPolicy` 的最小接口。
- token 摘要和常量时间比较辅助。
- 对象授权测试 fixture。

该模块不提供：

- 用户管理。
- 密码、OIDC、LDAP 或登录页面。
- 多租户。
- 通用 ACL/RBAC 管理后台。

Spring Security 到 `CurrentActorProvider` 的适配仍由 app 提供。

### 3.2 Data candidate 必须落库

不再保留“数据库或有界内存二选一”。v1.2.0 直接增加 `data_sql_candidates`：

- `candidate_id`
- `sql_text`
- `token_digest`
- `status`
- `owner_actor_id`
- `request_id`
- `model_name`
- `prompt_name/prompt_version/prompt_hash`
- `expires_at/consumed_at/created_at/updated_at`

候选表不保存完整用户问题；审计只通过 requestId 关联必要元数据。

### 3.3 token 只在创建响应中出现一次

- 服务端生成高熵随机 token。
- 数据库只保存 SHA-256 摘要。
- API 只在创建时返回明文 token。
- 查询、日志、审计、异常和后续响应都不再回显 token。
- v1.1 中尚未消费的明文 token 在升级到 V11 时统一失效，不尝试迁移为可继续使用的 token。

### 3.4 对象授权矩阵

| 动作 | ADMIN | OPERATOR | REVIEWER |
|---|---|---|---|
| 创建 Data/Support/Report/Resume 对象 | 允许 | 允许 | 拒绝 |
| 执行 Data candidate | 全部对象 | 仅自己创建 | 拒绝 |
| 确认普通 Support draft | 全部对象 | 仅自己创建 | 拒绝 |
| 处理 Support 人工复核队列 | 全部对象 | 仅允许取消自己的对象 | 仅明确进入 REVIEWER 队列 |
| 确认/取消/导出 Report | 全部对象 | 仅自己创建 | v1.2 不开放确认；`NEEDS_REVIEW` 仍不可确认 |
| 确认 Resume criteria | 全部对象 | 仅自己创建 | 拒绝 |
| 标记 Resume assessment REVIEWED | 全部对象 | 拒绝自审 | 仅明确进入 REVIEWER 队列 |
| 取消 Resume assessment | 全部对象 | 仅自己创建 | 仅分配给 REVIEWER 的对象 |

对象不可见或跨 owner 访问统一返回安全 404；合法对象的过期、重放和状态竞争返回稳定 409。

### 3.5 业务状态仍归各模块所有

不创建统一 confirmation 表或工作流表：

- Data 使用 `data_sql_candidates`。
- Support 使用 `support_reply_drafts` 和 `support_tickets`。
- Report 使用 `report_requests/report_drafts`。
- Resume 使用 `resume_jobs/resume_assessments`。

公共层只提供 actor、角色、token 摘要和访问策略，不保存业务状态。

### 3.6 审计 fail-open/fail-closed

| 场景 | 策略 |
|---|---|
| Data 外部 SQL 执行前审计意图 | fail-closed；没有审计记录不得执行 |
| Data 执行结果回写 | 尽力完成；失败产生运维错误，保留 PENDING/UNKNOWN 记录 |
| 平台库内确认、取消、复核状态变化 | 状态更新和审计同事务，fail-closed |
| 模型生成、低风险读取和诊断 | 审计 fail-open，不阻断只读响应 |
| 审计查询与清理任务 | 失败告警，不影响业务状态 |

## 4. 版本切片

### 4.1 v1.2.0：可信动作、对象授权和可靠确认

目标：先封闭跨 actor、明文 token、重放和并发状态风险。

主要交付：

1. 新增 `platform/common-security` 和 app Spring Security 适配。
2. Flyway V11：
   - 创建 `data_sql_candidates`。
   - 为 Support/Report/Resume 对象增加 owner、token digest、状态/动作操作者和复核队列字段。
   - 清理并失效旧明文 token。
3. Data candidate 改为 JDBC repository 和数据库条件消费。
4. Support 的 draft 状态与 ticket 状态在同一事务中做 expected-state 更新。
5. Report confirm/cancel/export 增加 owner 校验。
6. Resume criteria、assessment review/cancel 增加 owner/reviewer queue 校验。
7. 过期对象按模块配置定时清理或匿名化。
8. 新增 404/409 稳定错误契约。

测试矩阵：

- owner 成功、另一个 OPERATOR 失败。
- REVIEWER 只能处理明确队列对象。
- ADMIN 可处理全部对象。
- token 错误、过期、重放。
- 20～50 个并发确认请求只有一个成功。
- confirm/cancel 并发只有一个状态转换成功。
- 应用重启后 Data candidate 仍可按状态和有效期处理。
- V10→V11 历史升级保留业务数据并使旧 token 失效。

完成定义：

- 所有确认类接口不再依赖 URL 角色授权作为唯一边界。
- 数据库中不存在新写入的明文 confirmation/review token。
- 每个动作审计同时记录 creatorActorId 和 actionActorId。

### 4.2 v1.2.1：独立模块自动配置和审计 v2

目标：先让模块真实可复用，再让模型、Prompt、policy 和操作者审计准确。

主要交付：

1. 五个模块显式注册 Controller。
2. Data 增加明确 enabled 开关并保持默认兼容。
3. Resume 改为模块内 JDBC Repository，并在模块自动配置中受控注册。
4. 所有模块使用 `ConditionalOnClass/Bean/MissingBean/Property`，允许宿主覆盖。
5. 建立包名位于 `example.externalhost` 的最小外部宿主测试。
6. `AiChatService/AiEmbeddingService` 新增带元数据的结果：
   - provider、model、latency。
   - input/output/total tokens。
   - finish reason、provider request id。
7. `PromptTemplateService` 返回 prompt name、version、content hash 和渲染内容。
8. guardrail 结果统一记录 policyVersion 和稳定 violation code。
9. Flyway V12 增加审计 v2 字段和 retention/anonymized_at。
10. 默认保留策略：
    - 问题、SQL 和错误详情 7 天后匿名化。
    - 审计元数据 30 天后删除。
    - 可通过配置覆盖，但不能配置为负值或无限保留敏感正文。

测试矩阵：

- 五个模块在不扫描项目根包的 Web/ApplicationContext 中出现 Controller。
- enabled=false 时 Controller、Service 和 Repository 均不存在。
- 用户自定义 Bean 能覆盖默认实现。
- Knowledge retrieved IDs 与 cited IDs 分开且准确。
- Support/Report/Resume 不再写 `unknown` 模型。
- 客户端错误不含 provider、SQL、内部类名或堆栈。
- V11→V12 升级和保留任务有真实 PostgreSQL 测试。

### 4.3 v1.2.2：外部 PostgreSQL 查询目标

目标：把当前双 DataSource 配置升级为可诊断、可授权、可重复验证的外部 PostgreSQL 查询样板。

主要交付：

1. 在 Data 模块先定义窄接口：
   - `SqlDialect`
   - `SchemaMetadataDialect`
   - `ReadOnlyCapabilityInspector`
2. 提供 PostgreSQL 实现，当前 `col_description` 等逻辑移入该实现。
3. 增加 schema/table/column allowlist；未配置 column allowlist 时采用安全默认策略。
4. metadata、SQL 生成和执行前二次校验共享同一 dialect context。
5. 增加连接诊断：
   - 是否可连接。
   - 当前 dialect。
   - 是否只读。
   - 允许 schema/table 数量。
   - 权限缺口类别。
6. 诊断不得返回 URL、用户名、密码、SQL 原始异常。
7. 使用独立 PostgreSQL Testcontainer 作为业务查询库，不与平台库复用账号。
8. Data 查询通过 read-only transaction/session 执行，数据库角色继续作为第二道防线。

完成定义：

- 外部 PostgreSQL 库的 metadata、只读执行、越权拒绝和诊断测试通过。
- 平台 Flyway、审计和其他 Copilot 永远不使用业务查询 DataSource。

### 4.4 v1.2.3：MySQL 查询目标和双方法言契约

目标：在不改变平台 PostgreSQL + pgvector 的前提下，为 Data 增加 MySQL 业务查询目标。

主要交付：

1. 增加 MySQL Connector 和 MySQL Testcontainers 测试依赖。
2. 实现 MySQL：
   - catalog/database metadata。
   - 反引号标识符。
   - LIMIT/OFFSET。
   - 只读会话和权限诊断。
3. 禁止跨 database/catalog、存储过程、多语句和写操作。
4. PostgreSQL/MySQL 运行完全相同的只读查询契约。
5. 配置通过显式 dialect 或 JDBC URL 自动识别；识别冲突时启动失败关闭。
6. README 中英文分别提供 PostgreSQL/MySQL 最小权限账号示例。
7. CI 增加双方言契约测试；真实模型 smoke 仍通过显式 secret/profile 执行。

完成定义：

- PostgreSQL/MySQL 双 Testcontainers 全部通过。
- 任何方言都不能绕过 schema/table/column、函数、LIMIT 和资源上限。
- MySQL 不承载平台表、向量表和审计表。

每个 PR 都必须：

- 包含单元、上下文和必要 Testcontainers 测试。
- 更新对应模块文档和 Changelog。
- 前一 PR 未通过 CI 时不开始后一 PR 的实现提交。

## 6. 明确不做

- 第六个 Copilot。
- 多租户。
- 用户、组织、角色管理后台。
- 通用 ACL、工作流引擎或状态机平台。
- Redis、消息队列、微服务拆分。
- 在线保存任意数据库凭据。
- 多数据源租户路由。
- 跨库 JOIN、存储过程、DML/DDL。
- 商业 BI 和可视化查询构建器。

- PostgreSQL/MySQL 双业务查询库契约通过。

- README、模块 README、CHANGELOG、项目计划、模块计划和升级路线一致。
