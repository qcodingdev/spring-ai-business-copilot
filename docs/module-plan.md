# 模块详细规划

## 1. 模块设计原则

每个业务模块都必须满足：

- 业务场景明确。
- 输入输出清楚。
- 能独立 demo。
- 能复用平台能力。
- 有安全和审计边界。
- 有样例数据或样例文件。

模块不是功能堆叠，而是可交付的业务场景。

### 1.1 2026-07-18 五模块收口状态

- Data：相对日期、SQL guardrail、人工确认、只读执行和中文解释的真实浏览器闭环通过。
- Knowledge：TXT/Markdown/PDF/DOCX 有界解析、异步索引、可变向量维度、混合模型/维度隔离、服务端引用和有依据问答通过。
- Support：知识依据、人工修订、确认/取消和对象级复核边界通过。
- Report：手工/CSV/JSON 来源、草稿确认和 Markdown/HTML 导出通过。
- Resume：JD/简历文件、标准确认、证据评估、人工复核和隐私删除边界通过。

五模块中文真实模型 smoke 已全部通过。当前不增加第六模块，后续只处理远端发布门禁和真实部署反馈。

## 2. 第二模块选型结论

Data Copilot 之后，第二个模块优先选择：

> Knowledge Copilot：企业知识库助手

### 2.1 候选模块对比

| 模块 | 实用性 | 痛点强度 | Demo 独立性 | 实现风险 | 结论 |
|---|---|---|---|---|---|
| Resume Copilot | 中 | 中 | 高 | 中 | 场景清晰，但受招聘流程和合规边界影响较大 |
| Support Copilot | 高 | 高 | 中 | 中高 | 痛点强，但真实落地通常依赖客服系统、工单系统和知识库 |
| Knowledge Copilot | 高 | 高 | 高 | 中 | 最适合作为第二模块，痛点普遍且可独立闭环 |
| Report Copilot | 中 | 中 | 中 | 中 | 价值明确，但高质量报告依赖数据源、任务系统和会议记录 |

### 2.2 选择 Knowledge Copilot 的原因

- **覆盖面广**：几乎所有团队都有内部制度、产品文档、交付文档、运维手册、FAQ 难查的问题。
- **痛点真实**：新人上手慢、重复问答多、文档散落、知识无法沉淀，是中小团队和企业内部系统的高频问题。
- **闭环清楚**：上传文档、解析分片、检索问答、引用来源、审计记录，可以形成完整可演示链路。
- **依赖较少**：不强依赖招聘系统、客服系统、会议系统或第三方平台。
- **平台沉淀价值高**：可以沉淀文档解析、embedding、vector store、retrieval、citation、回答 guardrails 等能力。
- **与 Data Copilot 互补**：Data Copilot 面向结构化数据库，Knowledge Copilot 面向非结构化文档。

### 2.3 不优先选择其他模块的原因

- **Resume Copilot**：适合作品展示，但招聘筛选容易涉及偏见、歧视、隐私和“自动决策”风险，需要更强合规边界。
- **Support Copilot**：业务价值很高，但真正可用往往需要客服系统、工单状态、商品/订单信息和知识库联动，第二模块容易变重。
- **Report Copilot**：适合后续增强，但若没有稳定数据源和任务/会议输入，容易变成泛泛文本生成。

## 3. 第三模块选型结论

Knowledge Copilot 完成后，第三个模块优先选择：

> Support Copilot：智能客服助手

### 3.1 选择 Support Copilot 的原因

- **痛点强**：客服回复慢、口径不一致、重复问题多，是中小团队和 SaaS 团队非常常见的问题。
- **可以复用 Knowledge Copilot**：FAQ、退款政策、产品手册、故障处理流程都可以作为客服回复依据。
- **业务闭环清楚**：输入工单、分类、识别紧急程度、检索知识、生成回复草稿、人工确认、写审计。
- **可控风险**：MVP 只生成回复草稿，不自动发送，不直接承诺退款、赔偿、合同变更等高风险动作。
- **演示成本低**：可以用虚构客户、虚构工单和虚构知识库直接演示，不依赖真实客服系统。

### 3.2 初始 MVP 边界（历史）

以下边界用于说明第三模块最初如何从零落地；2.2 已在“不做完整客服平台”的前提下增加受控外部工单连接、SLA 风险提醒和确认后内部备注回写，当前能力以本文第 12 节和 `docs/support-copilot.md` 为准。

必须做：

- 工单文本输入。
- 工单分类。
- 情绪和紧急程度识别。
- 知识库依据检索。
- 回复草稿生成。
- 转人工建议。
- 高风险回复阻断或降级。
- 回复前人工确认。
- 回复审计日志。

初始 MVP 暂不做：

- 不接真实客服系统。
- 不自动发送消息。
- 不做多渠道会话聚合。
- 不做客服排班。
- 不做工单 SLA 流转或工作流编排。
- 不做订单/退款真实操作。
- 不做长期对话记忆。

### 3.3 与 Knowledge Copilot 的关系

Support Copilot 应优先复用 Knowledge Copilot 已经沉淀的知识检索和引用能力。

**V3 已实现完成（2026-07）。** Support Copilot 模块已实现，见 `docs/support-copilot.md`。

实现时要注意边界：

- Support Copilot 可以只读使用 Knowledge Copilot 的检索能力。
- Knowledge Copilot 不能反向依赖 Support Copilot。
- 如果复用点变多，再从两个模块共同使用的代码中沉淀到平台层。
- 回复草稿必须保留引用来源，不能把无依据内容包装成确定答案。

### 3.4 第四和第五模块顺序

Support Copilot 完成后，后续顺序调整为：

1. **第四模块 Report Copilot**：先复用 Data Copilot 的只读数据能力、Knowledge Copilot 的引用能力和 Support Copilot 的草稿确认模式，完成有来源的团队周报闭环。
2. **第五模块 Resume Copilot**：最后实现高合规要求的招聘辅助场景，只做逐条证据匹配和面试核验，不做候选人评分、排名、自动录用或淘汰。

选择 Report Copilot 优先于 Resume Copilot 的原因：

- Report Copilot 能直接复用前三个模块已验证的来源、guardrails、确认和审计能力。
- 周报和经营简报是团队高频工作，MVP 可使用虚构数据、任务和会议记录独立演示。
- Report Copilot 不直接参与高影响的人事决策，隐私和歧视风险低于招聘筛选。
- Resume Copilot 需要先明确受保护属性、证据边界和人工复核机制，放在最后更稳妥。

详细规划见 `docs/report-copilot.md` 和 `docs/resume-copilot.md`。

## 4. Data Copilot：数据库查询助手

### 4.1 总目标

让业务人员通过自然语言安全查询数据库。

### 4.2 核心用户

- 老板
- 运营
- 产品经理
- 数据分析薄弱的小团队
- 内部后台系统使用者

### 4.3 典型问题

- 上个月销售额是多少？
- 哪个商品退款率最高？
- 本周新增用户有多少？
- 不同渠道订单转化率如何？
- 客单价最高的用户群体是什么？

### 4.4 核心能力

- schema 读取和描述
- 自然语言转 SQL
- SQL 只读校验
- 查询确认
- 查询执行
- 结果脱敏
- 结果解释
- 查询审计

### 4.5 技术要点

- Spring Boot 4.1。
- Spring AI 2.0 ChatClient 结构化输出。
- JDBC 执行动态只读 SQL 和读取 schema metadata。
- Spring JDBC 负责候选、查询审计、动态只读 SQL 和 schema metadata，并通过条件更新保证一次性确认。
- JSQLParser 和确定性 validator chain。
- 集中式 prompt 模板和 audit log。

### 4.6 风险

- SQL 幻觉。
- 生成错误字段。
- 越权查表。
- 查询太慢。
- 敏感数据泄露。

### 4.7 防护

- schema 白名单。
- 只读 SQL。
- limit 限制。
- timeout 限制。
- 敏感字段脱敏。
- 执行前确认。

## 5. Knowledge Copilot：企业知识库助手

### 5.1 总目标

帮助团队基于内部文档快速获得有来源引用、可追溯、可审计的业务答案。

Knowledge Copilot 不是泛泛聊天机器人，而是面向企业内部知识检索和问答的助手。它必须基于已上传、已解析、已索引的知识内容回答；没有依据时必须明确回答不知道。

### 5.2 核心用户

- 新员工
- 客服和售后团队
- 实施交付团队
- 产品和研发团队
- 企业内部运营、行政、人事团队

### 5.3 典型问题

- 这个产品功能的开通条件是什么？
- 客户要求退款时应该走什么流程？
- 线上故障升级到 P1 的标准是什么？
- 新员工报销差旅费需要哪些材料？
- 某个接口的调用限制在哪里说明？
- 这份交付手册里对验收材料有什么要求？

### 5.4 2.0 核心能力

- 知识文档上传：支持 Markdown、TXT、PDF、DOCX，并限制文件和提取文本大小。
- 文档元数据管理：逻辑文档 ID、版本、标题、来源、业务分类、上传时间、索引和启用状态。
- 文档解析：提取纯文本，保留标题层级和段落位置。
- 文档分片：按标题、段落和长度切分，保留 source、section、chunkIndex。
- embedding 向量化：通过持久化异步任务生成向量，支持重试、失败状态和重建。
- 向量兼容：V17 使用不绑定维度的 pgvector 列；检索只比较相同 embedding model 和相同维度，历史数据不会拖垮当前查询。
- 混合检索：PostgreSQL 全文检索与 pgvector 共同召回 topK 相关片段。
- 答案生成：只基于召回片段回答。
- 来源引用：模型只选择本次召回的 chunk ID，引用片段和文档来源由服务端填充。
- 无依据拒答：召回结果不足或模型无法确认时回答不知道。
- 敏感信息处理：对手机号、邮箱、token、secret 等内容进行脱敏或阻断。
- 问答审计：记录问题、召回文档、引用片段、回答状态、模型名、耗时。

### 5.5 暂不做

- 不做复杂权限系统。
- 不做多租户。
- 不做企业级全文搜索后台。
- 不做文件协同编辑。
- 不做对话长期记忆。
- 不做绕过授权的企业资料抓取；只允许管理员配置的受控来源同步，ACL 映射失败时拒绝扩大可见范围。
- 不做大规模知识图谱。
- 不做流式回答，优先保证闭环。

### 5.6 输出

- 答案正文。
- 引用来源列表。
- 每条引用的文档标题、章节、片段摘要。
- 可信度提示。
- 无依据原因。
- 审计记录。

### 5.7 技术要点

- Spring AI ChatClient。
- Spring AI EmbeddingModel。
- PostgreSQL + pgvector。
- Spring JDBC 管理 document、chunk、问答审计、pgvector 写入和相似度检索。
- 文档解析和分片服务。
- prompt 模板集中管理。
- retrieval service。
- answer guardrails。
- audit log。

### 5.8 风险

- 模型根据常识编造答案。
- 引用片段和答案不一致。
- 检索召回不准。
- 文档内容过期。
- 文档中含有敏感信息。
- 未实现权限前误上传内部敏感文档。

### 5.9 防护

- Prompt 强制只基于召回片段回答。
- 回答必须携带 citation，没有 citation 不返回确定答案。
- 不接受模型自行改写的引用原文，excerpt 必须由服务端从本次召回 chunk 获取。
- 低相似度或召回不足时拒答。
- 答案生成后做引用完整性校验。
- 敏感字段默认脱敏，例如 phone、email、token、secret、password、id_card。
- 示例文档只使用虚构业务内容。
- 审计日志不记录完整文档原文，只记录文档 ID、chunk ID、片段摘要和状态。

## 6. Support Copilot：智能客服助手

### 6.1 总目标

帮助客服团队提升回复效率和工单处理质量。

### 6.2 核心用户

- 客服团队
- 售后团队
- SaaS 支持团队
- 小企业运营团队

### 6.3 核心能力

- 工单解析
- 知识库依据检索
- 工单分类
- 回复草稿
- 情绪识别
- 紧急程度判断
- 转人工建议
- 回复审计

### 6.4 输出

- 推荐回复草稿
- 引用依据
- 分类标签
- 情绪状态
- 紧急程度
- 转人工原因
- 回复风险提示

### 6.5 风险

- 错误承诺。
- 泄露用户隐私。
- 不合规回复。
- 情绪识别误判。
- 未经确认自动发送。

### 6.6 防护

- 高风险问题转人工。
- 回复前人工确认。
- 敏感信息脱敏。
- 回复模板约束。
- 回复草稿必须基于引用依据。
- 禁止自动发送。

### 6.7 技术要点

- Spring AI 2.0 结构化输出。
- Spring JDBC 管理 ticket、reply draft 和 support audit，并使用 expected-state 条件更新。
- Knowledge 检索通过窄接口适配。
- confirmation token 和状态流转由业务 service 控制，不交给 ORM。

## 7. Report Copilot：报表和周报助手

### 7.1 总目标

帮助团队基于可信业务指标、任务进展和会议记录生成有来源、可确认的结构化报告草稿。

### 7.2 核心用户

- 运营负责人
- 项目经理
- 团队负责人
- 中小团队管理者

### 7.3 核心能力

- 报告类型和统计周期输入
- 业务指标快照
- 任务和会议记录归一化
- 结构化周报生成
- 数据、事实和任务来源引用
- 事实与 AI 建议分离
- 人工确认
- Markdown 导出
- 生成审计

### 7.4 输出

- 执行摘要
- 指标亮点
- 已完成事项
- 风险和阻塞
- 来源行动项
- 明确标记的 AI 建议
- 来源索引
- Markdown 报告

### 7.5 风险

- 模型篡改数字。
- 编造任务、负责人和截止时间。
- 把建议包装成已决定事项。
- 误解会议结论或遗漏重要风险。
- 未经确认自动发布。

### 7.6 防护

- 指标值由确定性代码比对。
- 每个事实和任务必须引用 sourceId。
- AI 建议与来源行动项明确分离。
- 无依据内容进入 NEEDS_REVIEW。
- 只生成草稿，人工确认后才允许导出。
- 不执行 SQL、不修改任务、不自动发布。

### 7.7 技术要点

- 依赖框架加固后的 Spring AI 2.0 structured output。
- Spring JDBC 管理报告请求、来源、草稿和审计，确认/取消使用条件状态更新。
- 指标来源通过窄接口读取，不直接复用 Data Copilot 动态 SQL service。

详细设计见 `docs/report-copilot.md`。

## 8. HR Copilot：招聘与员工服务智能助手

### 8.1 总目标

把内部 `resume-copilot` 作为招聘辅助能力：生成岗位画像/JD、人工编辑并确认标准，再整理单份脱敏简历的证据、信息缺口和面试核验问题。员工制度问答复用 Knowledge 的 `HR_POLICY` 分类。

### 8.2 核心能力

- JD 标准解析和人工确认
- 岗位需求生成岗位画像和 JD 草稿
- 岗位标准人工编辑
- 简历脱敏和受保护属性移除
- 经历和技能证据抽取
- REQUIRED / PREFERRED 逐条匹配
- SUPPORTED / PARTIAL / NOT_FOUND / NEEDS_VERIFICATION 四态结论
- 证据引用和缺口分析
- 面试核验问题
- 人工复核和审计

### 8.3 风险

- 歧视性判断和受保护属性推断。
- 过度自动化招聘决策。
- 简历隐私泄露。
- 模型编造候选人经历。
- 把“简历未体现”错误表达为“不具备”。

### 8.4 防护

- 不生成总分、排名、通过概率、录用或淘汰建议。
- JD 标准必须人工确认。
- 受保护属性在模型调用前移除。
- 每项结论必须引用当前简历 evidenceId。
- NOT_FOUND 只表示简历未体现。
- REVIEWED 只表示人工阅读，不改变招聘流程。

### 8.5 技术要点

- 依赖框架加固后的 Spring AI 2.0 structured output。
- Spring JDBC 管理职位标准、脱敏简历、证据、评估和审计，模块不依赖宿主 Mapper 扫描。
- 隐私清理和受保护属性检测必须发生在模型调用前。

详细设计见 `docs/resume-copilot.md`。

## 9. 2.0 统一升级结论

五个业务模块不再按 v1.2～v1.6 分散发布，本轮统一作为 2.0 交付：

| 2.0 工作流 | 主模块 | 已完成升级 | 合并门槛 |
|---|---|---|---|
| 可信执行底座 | app + platform + Data | actor/object policy、摘要 token、条件状态更新、审计 v2、PostgreSQL/MySQL 查询目标 | PostgreSQL/MySQL 真实容器 |
| Knowledge 2.0 | Knowledge | 异步索引、多格式解析、版本、混合检索、citation 评测 | embedding 真实 smoke |
| Support 2.0 | Support | 枚举、状态机、知识版本、人工编辑反馈 | chat + Knowledge 真实 smoke |
| Report 2.0 | Report | 来源快照、新鲜度、CSV/JSON 导入、Markdown/HTML 导出 | 事实 groundedness smoke |
| Resume 2.0 | Resume | JD 版本、隐私保留/删除、人工纠正、代理歧视评测 | 合规 smoke 和删除验证 |
| 交付 2.0 | root/app | 非 root 容器、SBOM、依赖审查、Trivy、Dependabot | 所有远端 CI 通过 |

依赖原则：

- 2.0 分支未通过全部远端门禁和真实模型 smoke 前不得合并主干。
- PostgreSQL/MySQL 双方言共用一个窄 `BusinessDatabaseDialect` 边界，MySQL 不扩展为平台数据库。
- Support 只能通过 Knowledge 的窄检索接口复用能力。
- Report 只读取已配置指标快照，不调用任意 Text-to-SQL 执行接口。
- Resume 始终保持单候选人、逐条证据复核，不增加评分、排名和自动决策。
- 平台库保留 PostgreSQL + pgvector；MySQL 只作为 Data 的业务查询目标，不替换 Knowledge 向量存储。

2.0 的验收门槛和剩余外部门禁见 `docs/upgrade-roadmap.md`；当前审核证据见 `docs/current-project-audit-2026-07-16.md`，已经采纳的对象与安全边界见 `docs/decisions/`。

## 10. 2.1 质量与生产韧性结论

2.1 继续保持五个业务模块，不增加新 Copilot。共性能力只在 AI Core 沉淀，因为 Chat/Embedding 调用已被五个模块真实复用：

- 固定评测集覆盖 Data SQL 安全、Knowledge 引用、Support 禁止承诺、Report 来源一致性和 Resume 招聘合规。
- AI 子调用使用固定操作名、独立调用编号、中文日志和 Micrometer 指标。
- Spring AI 处理 HTTP 超时与受限重试；AI Core 处理并发隔离和 Chat/Embedding 独立熔断。
- 容量、备份和恢复保持脚本与运行手册形态，不引入调度平台或运维控制面。
- 外部工单、文档来源和 ATS adapter 已保持模块内窄接口；在至少两个真实部署场景证明复用前，不继续上移为通用连接器平台。

## 11. 五模块产品化与服务端场景目录

五个模块各提供 3 个固定场景，共 15 个。服务端场景目录保存操作白名单、内部数据范围、版本、内容哈希和预生成结果；业务接口只返回标题、说明、可编辑输入、业务化数据范围和是否有示例结果。

- Knowledge：自由提问，但只检索当前角色可见的系统虚构资料。
- Support：只使用虚构产品、政策和客户上下文，并提供人工复核队列。
- HR：岗位需求可编辑，简历只选择服务端预置虚构资源。
- Data：始终查询虚构只读数据库和场景表白名单，执行前展开 SQL。
- Report：用户只修改报告目标，固定虚构来源由服务端提供。

普通业务页不显示数据库 ID、内部枚举、Prompt、模型参数、确认 token 和 Token 用量；这些信息只在受控动作请求、折叠详情或私有管理台中使用。

## 12. 2.2 企业质量闭环

2.2 首先纵向升级 Knowledge，而不是新增业务模块：

- 每次问答在审计成功后返回稳定 `answerId`。
- 当前操作者只能对自己的问答提交或更新反馈。
- 无帮助反馈必须选择缺少依据、结论错误、资料过期、表达不清或其他稳定原因。
- `NO_EVIDENCE`、`REJECTED` 和负反馈进入 Admin/Reviewer 质量队列。
- Admin/Reviewer 必须填写说明后才能记录已处理、忽略或转知识维护。
- 处置绑定当前问题修订号和时间，旧页面不能覆盖新反馈；问题更新后自动重新入队。
- 工作台显示反馈、待复核和人工处置低基数计数，不把问题原文放入指标标签。
- 反馈只触发人工复核，不自动修改知识文档、检索阈值、Prompt 或模型。

后续真实资料来源、SSO 和工单 adapter 必须先在具体业务模块内验证；第二个复用场景出现后再评估平台 SPI。
